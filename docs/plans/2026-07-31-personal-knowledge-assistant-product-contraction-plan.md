## 1. 决策摘要

`llm-tutor` 不再继续发展为同时覆盖聊天、持久导师、测验、研究、学生画像、知识库、
Notebook、Space 和多层学习记忆的综合学习平台。

产品收缩为一个本地优先的个人知识助手：

> 用户管理自己的资料和笔记，助手基于明确选择的知识工作，给出可追溯答案，并在用户
> 授权下形成可查看、可修改、可删除的长期记忆。

目标产品保留五个一级入口：

1. **助手**：对话、资料问答、分析整理和受控知识操作。
2. **知识库**：管理用于 RAG 检索的只读资料。
3. **笔记**：记录、管理和查看用户拥有的 Markdown 笔记。
4. **记忆**：配置助手名称与行为，查看、开关、修改和遗忘长期记忆。
5. **设置**：模型、Embedding、数据、能力治理和外观。

Knowledge、Notebook 和 Memory 的底层成果继续使用；Quiz、Space、Student Profile、多 Tutor
和并列 Capability 模式退出目标产品。Research、联网搜索和代码执行降为助手按需调用的
能力，不再成为用户必须理解的独立产品模式。

## 2. 为什么现在需要收缩

当前产品已经拥有较完整的底层能力，但一级产品中心过多：

- Chat；
- Tutor；
- Knowledge；
- Notebook；
- Space；
- Memory；
- Quiz；
- Research；
- Organize / Code Exec 等 Capability。

这些模块分别成立，但放在同一个产品中会产生三个问题：

1. **核心承诺不清楚**：用户难以用一句话理解软件首先解决什么问题。
2. **入口与概念过多**：用户需要理解 Tutor、Memory、Space、Notebook 和不同模式之间的关系。
3. **维护面持续扩大**：每个模块都带来独立的 API、存储、恢复、UI、测试、文档和桌面 QA。

Knowledge/Memory 已完成 runtime 正式协议迁移，Notebook 也具备受控读写基础。现在适合用这些
已完成能力形成一个窄而完整的产品，而不是继续横向增加教学功能。

## 3. 产品定位

### 3.1 一句话定位

**一个真正了解你的资料、能帮助维护个人知识、且记忆始终由你控制的本地 AI 助手。**

### 3.2 核心用户

首个目标用户是需要长期处理个人资料的知识工作者和自学者，例如：

- 管理项目文档、会议材料和工作规范的人；
- 阅读论文、书籍和课程资料的研究者或学生；
- 使用 Markdown/Obsidian 维护个人笔记的人；
- 希望 AI 能延续偏好和任务背景，但不愿把全部数据交给云服务的人。

首版不再针对学校教学管理、教师、家长、班级或多人协作场景设计。

### 3.3 核心用户任务

产品必须优先做好以下任务：

1. 把散落的文档和笔记放进一个可搜索、可重建的个人知识空间。
2. 基于用户明确选择的资料回答，并能定位到真实来源。
3. 比较、总结和重组多份资料，而不是只返回相似片段。
4. 将有价值的结果保存为笔记，或安全地修改已有笔记。
5. 在用户明确控制下记住偏好、长期目标和未完成事项。
6. 让用户随时看见软件保存了什么、为什么保存以及如何删除。

### 3.4 非目标

目标产品不再负责：

- 课程教学路径和自适应学习；
- 测验生成、答题和题库管理；
- 学情分析、知识掌握度和学生画像；
- 多导师市场、导师交接和教学策略；
- 团队协作、账号、云同步和企业知识治理；
- 用一个统一界面暴露所有底层 Agent/Workflow 能力。

## 4. 产品原则

### 4.1 知识优先，Agent 隐于任务之后

用户关心的是“资料在哪里、答案依据什么、结果保存到哪里”，而不是当前运行了哪种 workflow。
工具调用和 trace 可以供高级用户检查，但不作为主要交互模型。

### 4.2 三类数据明确分离

| 数据域 | 含义 | 权威来源 | 默认 Agent 权限 |
| --- | --- | --- | --- |
| Sources / 资料 | 导入的 PDF、Markdown、文本、网页等参考材料 | 原始文件和文档记录 | 搜索、读取、引用；不修改原文 |
| Notes / 笔记 | 用户自己的知识成果和工作文档 | Markdown 文件 | 搜索、读取；明确授权后创建或编辑 |
| Memory / 记忆 | 偏好、长期目标、约定和连续性事项 | Memory store | 可关闭；写入和删除受控 |

读过资料不会自动产生记忆，聊天回答不会自动成为笔记，笔记内容也不会无提示地复制到
Memory。

### 4.3 本地优先且可退出

- 原始资料、笔记、记忆和 Session 默认保存在本地数据目录。
- 所有派生索引都可以从权威数据重建。
- 用户可以导出 Sources 清单、Markdown Notes、Memory 和会话数据。
- 使用远程 LLM 或 Embedding 时明确提示哪些内容可能发送给服务商。

### 4.4 引用不是装饰

凡是声称来自用户资料的事实，都应尽可能带可打开的来源和版本；无法验证时明确说明，
而不是生成一个看似可信的引用。

### 4.5 记忆始终可见、可控

- Memory 总开关默认清晰可见。
- 保存的记忆与历史检索是两个不同通道：前者是用户确认的长期条目，后者是可选的跨会话只读召回。
- 显式“记住”是保存长期条目的首选写入路径。
- 自动记忆不作为首版默认能力。
- 每条记忆都可查看来源、编辑、遗忘和关闭后续使用。
- 历史检索默认关闭，不能自动把旧对话晋升为保存的记忆；临时对话不读写记忆，也不进入未来历史索引。
- 保存的记忆预留全局和逻辑工作区作用域，但在工作区实体正式定义前只启用全局作用域。

### 4.6 不维护旧产品的双轨兼容

收缩采用直接切换：继续支持目标产品的数据域，旧教学数据文件不主动删除，但产品不提供
迁移、导入、归档，也不维护新旧导航、两套 Capability 模型或隐藏的教学工作流。

## 5. 目标信息架构

### 5.1 一级导航

```text
助手
知识库
笔记
记忆
设置
```

最近会话可以继续放在助手导航下方，不单独形成一级模块。

### 5.2 助手

助手页面负责：

- 新建和恢复会话；
- 选择本次会话可使用的知识库或知识范围；
- 发送文本、文件附件和知识条目引用；
- 展示流式回答、来源、必要运行状态和错误；
- 执行总结、比较、提取、写作和整理任务；
- 经授权创建或修改笔记；
- 经授权写入或删除 Memory；
- 将“深入研究”作为一次任务操作，而不是永久模式。

主输入框只暴露用户能理解的选择：

```text
资料范围 | 临时附件 | 模型（高级） | 发送
```

Quiz、Research、Organize、Code Exec 不再作为并列模式选择项。联网搜索、抓取和代码执行由
助手根据配置和任务按需调用，并通过 trace 或权限提示表达。

### 5.3 知识库

知识库页面只管理用于 RAG 的资料：

- 创建和重命名知识库；
- 导入 PDF、Markdown、Text 和后续支持的格式；
- 查看解析、切分、Embedding 和索引状态；
- 显示失败原因并支持重试或重建索引；
- 文件夹、标签、来源和更新时间过滤；
- 全局搜索、文档预览和引用定位；
- 重复文档检测、删除和导出。

### 5.4 笔记

笔记页面独立负责：

- Markdown 树、文件夹、标签、Wiki Link 和反向链接；
- 搜索、预览和编辑；
- 导入/导出 Obsidian 风格 Vault；
- Agent 受控创建、更新、重命名和移动；
- 基于 revision 的并发检查；
- 删除、批量修改和破坏性覆盖使用单独确认与恢复机制。

Knowledge Base 与 Notebook 保持不同的权威数据、检索方式和写权限；助手可在会话中按用户
选择调用两类来源，但界面不将二者混为同一个工作区。

### 5.5 记忆

记忆页面使用两个选项卡：“长期记忆”默认打开，负责总开关、记忆列表、来源检查、编辑和遗忘；
“助手配置”负责名称与行为说明。“长期记忆”区分用户确认的 Saved Memory 与默认关闭的
History Recall；后者只检索 runtime Sessions，不复制会话正文或自动形成长期条目。Memory 的
读取和变更仍通过 runtime access control 与 mutation gate，不因提升为一级页面而放宽权限。

### 5.6 设置

设置收敛为以下分组：

1. **模型**：LLM 配置、测试和默认选择。
2. **检索**：Embedding、搜索服务、索引默认参数。
3. **能力治理**：允许使用的工具、预算和审批策略。
4. **数据与隐私**：数据目录、备份、导入导出、远程数据发送说明。
5. **外观与帮助**：主题、语言、快捷键和简化后的首次引导。

## 6. 核心用户流程

### 6.1 建立知识库

```text
创建知识库
-> 添加资料
-> 查看处理进度
-> 处理成功或修复失败
-> 搜索并预览
-> 在助手中使用
```

验收重点不是“上传接口返回成功”，而是用户能理解文档当前是否可被搜索，以及失败后如何
恢复。

### 6.2 基于资料完成任务

```text
选择资料范围
-> 提问或描述任务
-> 助手 search/read
-> 返回答案和可打开引用
-> 用户继续追问或保存为笔记
```

### 6.3 维护个人笔记

```text
用户要求整理资料
-> 助手读取 Sources / Notes
-> 生成新笔记或提出修改
-> 非破坏性明确请求可直接执行
-> 自发或破坏性修改要求确认
-> 返回最终文件和 revision
```

### 6.4 形成长期记忆

```text
用户明确说“记住……”
-> 助手提出 Memory mutation
-> runtime authorization + mutation gate
-> 保存 provenance / revision
-> 后续会话按需检索
-> 用户可随时查看、修改或遗忘
```

跨会话找回旧讨论使用独立流程：

```text
用户开启历史检索
-> 当前问题确实需要旧对话
-> 按权限和作用域搜索 runtime Sessions
-> 精确读取相关 turn 并显示可打开来源
-> 只用于本轮回答，不自动写入 Saved Memory
```

## 7. 功能取舍

| 当前能力 | 目标决策 | 处理方式 |
| --- | --- | --- |
| Chat / Session | 保留并强化 | 成为唯一主工作台 |
| Knowledge / RAG | 保留并强化 | 成为 Sources 管理核心 |
| Notebook | 保留并强化 | 成为独立的 Notes 记录、管理和查看工作区 |
| Learner Memory | 保留并改名 | 收缩为独立 Memory 页中的 User Memory |
| Tutor Memory | 合并 | 收缩为单一 Assistant Continuity |
| Tutor Soul | 简化 | 变成单一助手的行为设置 |
| 多 Tutor 管理 | 删除 | 不保留并行身份、交接和权限矩阵 |
| Research | 降级为任务 | 从模式变为聊天中的“深入研究”操作 |
| Web search/fetch | 保留为工具 | 不占据独立导航或模式 |
| Code execution | 可选工具 | 默认隐藏在高级能力中 |
| Quiz / Quiz Bank | 删除 | 导出已有数据后删除工作流、UI 和存储 |
| Student Profile | 删除 | 有价值的个人偏好迁入 User Memory |
| Space | 删除 | Notebook 独立保留，其余 Space 聚合入口退出 |
| Organize mode | 删除 | 由普通助手直接执行笔记任务 |
| Deep Solve | 保持退休 | 不恢复旧入口或兼容路径 |
| Trace | 保留但弱化 | 默认折叠，供高级用户和故障诊断使用 |

## 8. 技术架构边界

### 8.1 runtime 继续负责

- Run、Session、上下文构建和 compaction；
- Tool orchestration、Hook、trace 和 cancellation；
- KnowledgeSource、search/read、AccessControl 和 Citation；
- Session Projection 与可信 Evidence；
- MemoryService、MemoryStore、mutation gate 和 provenance；
- ContextAttachment 合并后提供的临时资料生命周期。

### 8.2 产品继续负责

- 文档导入、解析、切分、Embedding 和 LanceDB；
- Sources/Notes/Memory 的产品数据模型和 UI；
- Notebook 文件操作、索引、CAS 和恢复；
- 具体的检索组合、排序和 token 分配；
- 助手行为、工具配置和记忆产品策略；
- 本地数据、导入导出、桌面交互和隐私说明。

### 8.3 不允许的新技术债

- 不在产品中重新实现 parallel runtime；
- 不为旧 Capability 建兼容 facade；
- 不把 Sources、Notes 和 Memory 合并成一个无差别文档 store；
- 不用 prompt 代替服务端权限和 mutation gate；
- 不长期隐藏已废弃模块而继续维护其 API、恢复和测试；
- runtime 缺口记录到 `docs/framework-feedback.md`，跨仓库决策通过 issue 持久沟通。

## 9. 分阶段改造计划

### Phase 1：确定产品边界

一句话：把产品正式定义为“本地优先的个人知识助手”，冻结教学功能扩张并确定删除清单。

- [x] 评审并接受本文档；
- [x] 产品名称确定为 Folumi，并创建目标 GitHub 仓库；
- [ ] 完成商标、域名、应用商店和软件著作权核验；
- [x] 更新 PRD、README、MANUAL 和验收基线；
- [x] 盘点 Quiz、Space、Tutor 和 Student Profile 的用户数据导出需求；
- [x] 冻结这些模块的新功能开发。

验收：团队能用同一句话描述产品，所有现有模块都有明确的保留、合并或删除决策。

### Phase 2：收缩产品界面

一句话：导航明确为“助手、知识库、笔记、记忆、设置”，让三个长期数据域各自拥有清晰的
工作区，同时把 Research 保持为助手任务动作。

- [x] 重构 AppView 与 Sidebar；
- [x] Knowledge Base 保持为只包含 RAG Sources 的独立页面；
- [x] Notebook 作为记录、管理和查看笔记的独立一级页面；
- [x] Memory 作为记忆开关、审阅、编辑和遗忘的独立一级页面；
- [x] Research 改为聊天任务动作；
- [x] 删除 Capability 模式选择器中的 Quiz、Research 和 Organize；
- [x] 重写首次引导和空状态。

验收：新用户不需要理解 Tutor、Space、Memory 层级或 workflow 名称即可完成首次资料问答。

### Phase 3：强化知识库管理

一句话：把投入集中到资料处理透明度、检索、预览、引用和可恢复性，使知识库本身达到可长期
使用的质量。

- [x] 统一导入状态和失败原因；
- [x] 增加重试、重建索引和重复检测；
- [x] 完善全局搜索、过滤和预览；
- [x] 打通引用到原始文档位置；
- [x] 完成 Sources 与 Notes 的联合搜索；
- [x] 验证所有索引都能从权威数据重建。

验收：用户能独立判断资料是否可用，能够从回答追溯到来源，也能恢复损坏或过期的索引。

### Phase 4：完善个人助手

一句话：建立单一助手体验，使其能基于指定资料工作、受控维护笔记，并让记忆对用户完全透明。

- [x] 将多 Tutor 收缩成一个 Assistant Profile；
- [x] 将 Assistant Profile 的名称和行为配置归入独立 Memory 页面；
- [x] 在 Memory 内用“长期记忆 / 助手配置”两个选项卡分离两类操作；
- [x] 明确显示每个会话正在使用的资料范围；
- [x] 完成 Notes 创建、更新、移动、删除确认和恢复闭环；
- [x] 按修订提案实现 Saved Memory、冲突失效规则和全局作用域；旧 Tutor 私有连续性不读取、
  不导入，也不静默合并到当前记忆；
- [x] 增加 Memory 总开关、逐项来源、编辑、完成、置顶和彻底遗忘；
- [ ] 在 runtime 跨 Session 检索边界可用后，实现默认关闭的 History Recall、临时对话和来源跳转；
- [ ] 通过单独产品决策定义逻辑工作区后启用 workspace 作用域，不把 Knowledge Base、Notebook
  或单个 Session 当成工作区；
- [ ] 使用 ContextAttachment 支持临时资料，但不默认自动召回（runtime
  尚无一等临时附件边界，已记录到 `docs/framework-feedback.md` 和
  [llm-harness-runtime#101](https://github.com/oh-my-harness/llm-harness-runtime/issues/101)，产品侧不建设平行实现）。

验收：用户可以用一个助手完成“查资料—形成答案—保存笔记—延续偏好”的完整任务，并能
解释所有长期数据如何产生。

### Phase 5：删除旧功能

一句话：新闭环通过桌面验收后，直接删除教学平台遗留代码，不保留隐藏双轨。

- [x] 删除 Quiz、旧 Tutor 数据迁移和归档导出能力，遗留文件原地保留但不参与运行；
- [x] 删除 Quiz workflow、UI、API、存储和恢复逻辑；
- [x] 删除 Space 页面和聚合模型，以 Notes 接口替代产品侧聚合入口；
- [x] 删除多 Tutor 管理、交接和教学专属状态；
- [x] 删除废弃 Capability 分支、旧事件和测试；
- [x] 清理文档、依赖和无引用资产；
- [x] 运行完整 Rust、前端和桌面 acceptance gate。

验收：仓库只包含目标产品实际使用的能力，旧教学模块不再增加构建、测试和维护成本。

## 10. 数据保留与旧功能删除策略

产品收缩继续保护目标数据域，但不为旧教学模型维护迁移能力：

1. Sessions、Settings、Notebook 文件和 Knowledge Base 原始文档继续保留；
2. 旧分层 Memory 和已经退役的 runtime Memory 后端数据不读取、不转换、不导入新系统；
3. Tutor 私有连续性、Quiz、Student Profile 与旧 workflow 数据不读取、不转换、不导出；
4. Folumi 不主动删除这些遗留文件，需要保留时由用户直接备份应用数据目录；
5. 派生索引可从权威 Sources 重建；
6. 不提供旧读取路径、迁移 API、双写或隐藏兼容入口。

## 11. 质量与验收指标

### 产品指标

- 首次启动到第一次带引用回答所需步骤；
- 文档导入成功率和失败可恢复率；
- 引用可打开率和引用覆盖率；
- 用户完成“查找—回答—保存笔记”任务的成功率；
- 用户能否找到并删除一条 Memory；
- 一级导航、设置项和首次引导步骤的数量。

### 工程门禁

- Sources、Notes 和 Memory 不发生隐式复制；
- Knowledge 引用必须通过 runtime Evidence 验证；
- Notes 修改具备 root confinement、revision 和恢复路径；
- Memory mutation 必须经过 access control 和 mutation gate；
- Session replay 不恢复 ephemeral 正文；
- 删除旧模块后无悬空 API、事件、数据恢复分支或文档承诺；
- Rust workspace、前端测试/构建和桌面 smoke QA 全部通过。

## 12. 品牌决策：Folumi

### 12.1 名称含义

产品正式采用 **Folumi**：

- `Folio` 表示用户拥有的资料、笔记和个人知识集合；
- `Lumi` 来自 light / illuminate 的联想，表示把需要的知识照亮；
- 三音节名称容易发音，又比常见的两音节助手名更有搜索辨识度；
- 名称没有 Tutor、RAG 或 Memory 的功能限制，可以随产品长期演进。

建议品牌表达：

```text
Folumi
Your friendly knowledge companion.

Bring your knowledge to light.
```

中文产品描述使用“本地个人知识助手”，不另设一个与 Folumi 并列的中文主品牌。需要人格化
表达时，可以把产品中的助手称为 **Lumi**，但 `Lumi` 不是独立产品、账号或第二套品牌。

### 12.2 品牌原则

- 产品界面统一使用 `Folumi`，不混用 Tutor Agent、归知或 llm-tutor；
- `Personal Knowledge Assistant` 是品类描述，不是产品名；
- 图形方向可以使用“被照亮的 Folio、书页或知识微光”，避免猫头鹰、毕业帽等教学符号；
- 品牌语气友好、清楚、可信，不使用“全知大脑”“永不遗忘”等无法验证的承诺；
- 正式发布前完成商标、软件著作权、应用商店、域名和主要社交平台核验。

### 12.3 已放弃的命名方向

- **Tutor Agent / llm-tutor**：继续强化教学预期，与收缩后的通用个人知识产品不一致。
- **归知**：不再作为主品牌，避免中英文双品牌增加认知成本。
- **知伴**：已有 App 和多个 AI 陪伴/学习产品，冲突明显。
- **知屿**：已有知识和“第二大脑”相关产品，定位接近。
- **Lorekeep、Knota、Knovia/Knovera**：已有知识管理、文档 AI 或学习助手产品。
- 含 `GPT`、`RAG`、`LLM` 的名称：暴露实现细节，且不利于产品长期演进。

## 13. 仓库与技术名称迁移

目标产品仓库确定为 `oh-my-harness/Folumi`。该仓库在 2026-08-01 确认为公开空仓库，尚无
默认分支。

迁移采用一次性切换，不长期维护 `llm-tutor` 与 `Folumi` 两个活跃仓库：

1. 在 `llm-tutor` 合入本改造决策并冻结与目标产品无关的新功能；
2. 将完整 Git 历史推送到 `Folumi`，保留架构决策、问题修复和作者记录；
3. 从切换点开始只在 `Folumi` 开发产品收缩，旧仓库不接受功能回迁；
4. `llm-tutor` 在 Folumi 可构建并完成首次基线发布后设为只读归档，并在 README 指向新仓库；
5. 不使用两个仓库间的同步脚本、cherry-pick 队列或兼容发布分支。

代码中的正式技术重命名在 Phase 2 信息架构稳定后一次完成，并包含：

- 桌面产品名和图标；
- Tauri bundle identifier；
- 前端标题与本地化文案；
- 默认数据目录兼容性；
- GitHub 仓库说明与 README；
- Rust crate 中确实面向产品的命名。

runtime crate、Knowledge/Memory 协议和内部通用类型不随品牌重命名。旧数据目录继续保留
现有键，不提供产品内迁移或双写。Git 历史中保留旧名称是正常的审计记录，不做破坏性的
历史重写。

## 14. 最终验收场景

目标产品至少通过以下桌面端场景：

1. 新用户配置模型和 Embedding，创建知识库并导入三份资料。
2. 用户看见每份资料的处理状态，并成功修复一份导入失败的文档。
3. 用户要求比较三份资料，助手返回带可打开引用的差异和建议。
4. 用户要求将结论保存为 Markdown 笔记，随后让助手基于 revision 修改该笔记。
5. 用户明确要求记住一个回答偏好，并在新会话中看到该偏好生效。
6. 用户在设置中查看偏好的来源并将其遗忘，后续会话不再使用。
7. 用户导出 Sources 清单、Notes、Memory 和 Session 数据。
8. 整个流程不出现 Quiz、Space、Student Profile、多 Tutor 或 workflow 专有概念。

完成这一场景后，产品才算真正从“功能很多的 Tutor 原型”收缩为“清晰、可信、可长期使用
的个人知识助手”。
